## Acceptance review

- PostgreSQL driver, versioned migrations, explicit storage configuration: implemented; real workflow successful.
- Offline SQLite backup/transfer, occupied-target refusal, semantic state equality and rollback guidance: implemented and exercised by the real PostgreSQL workflow.
- Existing API lifecycle, ownership, concurrency, revisions and photo protection: shared suite rerun against PostgreSQL in the successful workflow; local memory/SQLite regressions independently passed.
- Restart durability, single-writer exclusion and transactional rollback: included in real PostgreSQL tests. Dedicated QueryRunner holds a session advisory lock; additional writers reject startup, and lost connections fail closed rather than silently reconnecting unlocked.
- Readiness: database connection checked before API access; health responds 503 when unavailable.
- Scaling limits: explicitly documented as one cached application writer, not multi-instance high availability.

## Defect and required regression

`openapi.yml` still restricts successful `/api/health` storage to `memory | sqlite`, so `{status: "ok", storage: "postgres"}` violates the authoritative contract. Newly introduced readiness 503 responses and `STORAGE_UNAVAILABLE` API errors are also undocumented. The old structural checker did not detect this.

Reproduction: read `paths["/api/health"].get.responses["200"].content["application/json"].schema.properties.storage.enum` and compare the implemented PostgreSQL health response.

Expected correction: document PostgreSQL health, health 503 and relevant API 503 responses, and add regression assertions that fail on their absence. Engineer must repair and QA must retest before closure. QA posted the finding on the real issue and left it open.
